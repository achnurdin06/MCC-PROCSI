ARCH-MOD-01

1.1 Latar Belakang & Tujuan Rekayasa

ETL Migration Command Center didesain secara khusus untuk menjawab tantangan migrasi data kritikal berskala enterprise pada ekosistem rantai pasok PT ANTAM Tbk. Sistem ini menghubungkan database warisan Microsoft SQL Server (antam_scm) dengan platform inti modern berbasis PostgreSQL (db_procsi). Seluruh operasi data dipagari oleh mekanisme isolasi ketat untuk menjamin ketiadaan mutasi pada data asli sistem sumber.

1.2 Diagram Arsitektur 3-Tier Pipeline

Alur data bergerak linear melalui pemisahan tiga lapis database fisik dan logika isolasi transaksional:

TIER 1 database

Source DB (Read Only)

MS SQL Server (antam_scm)

Schema dbo. Hanya diakses melalui objek View terkontrol.

Objek: v_migration_*
Akses: Read-Only via SSH
TIER 2 swap_horiz

Staging Engine

PostgreSQL (db_procsi)

Schema isolasi stg_antam. Transformasi struktur & normalisasi kode.

Tabel: stg_*_src
Lookup Engine & Validation
TIER 3 inventory_2

Target Production

PostgreSQL (db_procsi)

Schema vendor / core. Data hidup dengan tagging audit permanen.

Flag: migration = '1'
Tracking: migration_run_id
Alur Eksekusi Terintegrasi:
Flow 1: Ekstraksi & Lookup arrow_forward Flow 2: Posting Valid & Sync ID arrow_forward Flow 3/4: Safe Rollback/Purge

1.3 Sistem Pengamanan Berlapis (Dual-Guard Protection)

Untuk memastikan integritas data produksi existing tidak pernah terganggu oleh siklus migrasi, arsitektur menerapkan mekanisme pengunci ganda (Dual-Guard):

security Guard 1: Strict Tag Isolation

Setiap baris data hasil migrasi yang diposting ke tabel produksi mutlak disuntik kolom audit migration = '1' dan migration_run_id = <UUID>. Operasi pembersihan atau rollback tidak akan pernah menyentuh data dengan status non-migrasi (migration = '0' atau NULL).

verified_user Guard 2: Staging Hash Reference

Sebelum eksekusi posting atau purges data dilakukan, sistem mencocokkan Primary Key dan Hash integritas pada tabel target dengan rekaman di tabel staging (stg_*_src). Apabila referensi staging tidak ditemukan, operasi otomatis digugurkan seketika (Hard Abort).

1.4 Konektivitas Jaringan & Auto-Healing SSH Tunnel

Akses ke SQL Server production di segmen VLAN tertutup dikelola melalui tunnel SSH reverse berkala:

TOPOLOGI JARINGAN AMAN PORT FORWARDING
HOST_REDACTED:22 (SSH Gateway) ➔ 127.0.0.1:11433 ➔ MS SQL Server (antam_scm:1433)
Auto-Healing Daemon: Memeriksa koneksi setiap 30 detik. Jika putus, proses re-handshake dieksekusi dalam tempo < 2.500 ms tanpa menghentikan worker pipeline.

Menu 2: Migration Config & Rules Engine

CONFIG-CORE-05

Menu Migration Config adalah jantung penerjemah struktur data. Di sini, insinyur ETL memetakan satu View SQL Server menjadi target PostgreSQL (mendukung relasi 1-View ke Multi-Target).

account_tree Prinsip Wajib Foreign Key (exec_order)

Tabel PostgreSQL memiliki foreign-key constraint ketat. Oleh sebab itu, parameter exec_order harus diurutkan dari tabel induk (Parent) menuju tabel anak (Child). Contoh urutan valid: exec_order = 1 (Master Vendor) ➔ exec_order = 2 (Vendor Contact) ➔ exec_order = 3 (Vendor Bank Account).

Arsitektur 4 Sub-Tabel Metadata Konfigurasi

1. migration_config Definisi View sumber, target staging, urutan exec_order, dan kondisi WHERE clause filter awal.
2. migration_convert_rule Kamus aturan konversi tipe data (misal: casting BIT MSSQL ke BOOLEAN PG, string sanitize, default values).
3. migration_target_config Pemetaan field staging ke satu atau lebih tabel produksi di skema vendor atau skema relasi lain.
4. migration_lookup Kamus penerjemah ID antar sistem (misal: kode unit bisnis lama di ANTAM dipetakan ke UUID baru di SCM Cloud).

Workflow Canvas Studio adalah pusat orkestrasi visual berbasis Directed Acyclic Graph (DAG). Operator dapat memantau pergerakan batch data secara real-time melalui 4 preset pipeline baku:

Mengambil data dari SQL Server, menyimpannya di stg_antam.stg_*_src, dan menjalankan lookup engine. Data target belum disentuh sama sekali.

Syarat: Flow 1 Harus SUCCESS Auto-Sync Sequences
FLOW 3: SAFE ROLLBACK Order DESC

10.1 Alur 8 Tahapan SOP Migrasi Produksi

Setiap migrasi wajib mematuhi 8 tahapan terstruktur di bawah ini guna meminimalkan risiko operasional:

1

Persiapan & Verifikasi SSH

Pastikan ketiga indikator database pada header menyala hijau stabil.

2

Inspeksi View Sumber (Menu 1)

Cek jumlah baris pada v_migration_* dan pastikan tidak ada skema field yang berubah.

3

Validasi Aturan Konversi (Menu 2)

Verifikasi urutan exec_order foreign key dan mapping kolom lookup.

4

Eksekusi Flow 1 (Staging Landing)

Tarik data ke skema stg_antam. Pantau log terminal hingga status SUCCESS.

5

Audit Data Staging

Lakukan verifikasi kecocokan baris awal antara SQL Server dengan Staging Table.

6

Eksekusi Flow 2 (Posting Target)

Jalankan chunking posting 1.000 baris. Biarkan sistem menyelaraskan PostgreSQL sequences.

7

Rekonsiliasi Akhir 3-Tier (Menu 4)

Bandingkan total baris ketiga tier. Pastikan indikator presisi menampilkan 100% MATCH.

8

Penerbitan Berita Acara Resmi

Kunci batch transaksi dan unduh dokumen Berita Acara PDF untuk tanda tangan resmi para pihak.

10.2 Pertanyaan Umum (FAQ) & Penyelesaian Gangguan

Flow 2 menerapkan proteksi deterministik. Run ID hanya diizinkan diposting apabila eksekusi Flow 1 yang menaunginya memiliki status mutlak SUCCESS dan belum pernah diposting sebelumnya. Apabila status berbunyi FAILED atau SUPERSEDED (kadaluarsa oleh penarikan data baru), posting otomatis ditolak demi mencegah ketidaksinkronan data.

Penyebab utama kendala ini adalah ketidakcocokan urutan pada konfigurasi exec_order (Menu 2). Pastikan tabel referensi utama (Parent, misal vendor_master) diberi exec_order: 1, lalu tabel anak (misal vendor_contact) diberi exec_order: 2. Jika terjadi pada saat rollback, pastikan Flow 3 menghapus dengan urutan terbalik (ORDER BY exec_order DESC).

Sistem memiliki daemon *Auto-Healing* yang otomatis mencoba re-koneksi dalam waktu 30 detik. Namun apabila tetap terputus, buka menu Master Settings pada header, masuk ke tab Connection String, dan klik tombol "Restart Tunnel Daemon". Pastikan port lokal 11433 tidak terblokir oleh proses sistem operasi lainnya.

100% Dijamin Aman. Mekanisme Dual-Guard Protection memastikan klausul SQL DELETE pada Flow 4 selalu memuat predikat pengunci ganda: WHERE migration = '1' AND EXISTS (SELECT 1 FROM stg_antam.stg_*_src ...). Seluruh data transaksi yang dimasukkan secara organik oleh staf melalui portal vendor memiliki nilai migration = '0' atau bernilai NULL sehingga kebal terhadap operasi pembersihan.
